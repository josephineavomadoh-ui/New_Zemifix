## 1. Corrected AUTH Realm Database Access & Security Architecture

When Migration `20261119000002_stage2_1_default_deny_rls` is applied, default-deny RLS requires `app_security_context_valid()` for all queries executed by `zemifix_app_user`. Unauthenticated users submitting login credentials or requesting OTPs do not possess a session token or `userId`.

### 1.1 Support for Unauthenticated `'AUTH'` Security Realm
In `src/lib/services/securityContextService.ts`, line 118 currently validates:
```typescript
if (!context.userId && context.realm !== 'WORKER' && context.realm !== 'PUBLIC_QR') {
  throw new Error('SECURITY_CONTEXT_MISSING: Authenticated user context is required for this realm.');
}
```
**Required Update:** `securityContextService.ts` must be updated to exempt `realm === 'AUTH'` when `userId` is empty (`""`):
```typescript
if (!context.userId && context.realm !== 'WORKER' && context.realm !== 'PUBLIC_QR' && context.realm !== 'AUTH') {
  throw new Error('SECURITY_CONTEXT_MISSING: Authenticated user context is required for this realm.');
}
```

### 1.2 HMAC Signature Payload Compatibility
In `20261119000001_stage2_1_signed_security_context/migration.sql`, the payload calculation converts empty `userId` (`""`) to length-prefixed string `'0:'`. The HMAC signature generated by `withSecurityContext({ realm: 'AUTH', userId: '' })` is mathematically valid and fully verified by `app_security_context_valid()` in PostgreSQL.

### 1.3 Operation-Specific Database Access Policies for `'AUTH'` Realm

To prevent unrestricted anonymous access, database queries under `'AUTH'` realm are restricted to narrowly scoped, operation-specific policies:

```sql
-- 1. Password Login User Lookup Policy
-- Allows searching active users by login email strictly during authentication bootstrap
CREATE POLICY stage2_auth_user_lookup ON public.users
FOR SELECT TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
  AND "isActive" = true
  AND "deletedAt" IS NULL
);

-- 2. OTP Challenge Management Policy
-- Allows creating, reading, and updating OTP rows strictly during login/MFA verification
CREATE POLICY stage2_auth_otp_bootstrap ON public.auth_otps
FOR ALL TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
)
WITH CHECK (
  public.app_realm() = 'AUTH'
);

-- 3. Customer Portal Contact Login Lookup Policy
CREATE POLICY stage2_portal_contact_lookup ON public.customer_contacts
FOR SELECT TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
  AND "isActive" = true
  AND "deletedAt" IS NULL
);
```

### 1.4 Protection Against Authentication Abuse Vectors
- **User Enumeration Protection:** Login handlers execute constant-time bcrypt password comparisons against `DUMMY_HASH` (`auth.ts#L100`) when an email is unknown, ensuring response times are indistinguishable.
- **OTP Brute-Force & Replay Protection:** `auth_otps` enforces 5-minute expiration windows and locks challenge rows after 3 failed attempts (`attemptCount >= 3`). Consumed OTPs set `consumedAt = now()` and cannot be re-used.
- **IP Rate Limiting:** All authentication endpoints (`/api/auth/login`, `/api/auth/verify-otp`, `/api/portal/auth/login`) enforce strict IP rate-limiting buckets (`rateLimitService.ts`).

## 4. Transaction-Client Compile-Time & Static-Analysis Enforcement

To prevent developers from accidentally importing the root `prisma` client inside protected services or bypassing security context transactions:

1. **Mandatory Service Signatures:** All service functions in `src/lib/services/` MUST require `tx: Prisma.TransactionClient` as their first parameter:
   ```typescript
   export async function createWorkOrder(
     tx: Prisma.TransactionClient,
     user: AuthenticatedUser,
     data: WorkOrderInput
   ) { ... }
   ```
2. **ESLint Restricted Import Rule:** Configure `.eslintrc.json` rule prohibiting root `prisma` imports in service and route modules:
   ```json
   "no-restricted-imports": [
     "error",
     {
       "paths": [
         {
           "name": "@/src/lib/prisma",
           "importNames": ["prisma"],
           "message": "Direct use of root prisma client in services/routes is prohibited. Use the transaction client 'tx' provided by withSecurityContext."
         }
       ]
     }
   ]
   ```
3. **Runtime Uninitialized Transaction Rejection:** If a service receives a transaction client without registered security context, `withSecurityContext` throws `UNINITIALIZED_TRANSACTION_CONTEXT`.
