## 1. Corrected AUTH Realm Database Access & Security Architecture (Issue 1)

In previous drafts, allowing `FOR ALL ON auth_otps USING (app_realm() = 'AUTH')` was overly permissive. Revision 11 corrects this by introducing **Narrowly Scoped Operation-Specific Policies** for the `'AUTH'` realm.

### 1.1 Support for Unauthenticated `'AUTH'` Security Realm
In `src/lib/services/securityContextService.ts`, line 118 is updated to exempt `realm === 'AUTH'` when `userId` is empty (`""`):
```typescript
if (!context.userId && context.realm !== 'WORKER' && context.realm !== 'PUBLIC_QR' && context.realm !== 'AUTH') {
  throw new Error('SECURITY_CONTEXT_MISSING: Authenticated user context is required for this realm.');
}
```

### 1.2 HMAC Signature Payload Compatibility
In `20261119000001_stage2_1_signed_security_context/migration.sql`, empty `userId` (`""`) converts to `'0:'` in the length-prefixed payload string. The HMAC signature generated by `withSecurityContext({ realm: 'AUTH', userId: '' })` is mathematically valid and fully verified by `app_security_context_valid()` in PostgreSQL.

### 1.3 Operation-Specific Database Access Policies for `'AUTH'` Realm

```sql
-- 1. Password Login User Lookup Policy (SELECT Only)
CREATE POLICY stage2_auth_user_lookup ON public.users
FOR SELECT TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
  AND "isActive" = true
  AND "deletedAt" IS NULL
);

-- 2. OTP Creation Policy (INSERT Only)
CREATE POLICY stage2_auth_otp_insert ON public.auth_otps
FOR INSERT TO zemifix_app_user
WITH CHECK (
  public.app_realm() = 'AUTH'
  AND "consumedAt" IS NULL
  AND "invalidatedAt" IS NULL
  AND "attemptCount" = 0
  AND "expiresAt" > now()
);

-- 3. OTP Lookup & Verification Policy (SELECT Only)
CREATE POLICY stage2_auth_otp_select ON public.auth_otps
FOR SELECT TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
  AND "consumedAt" IS NULL
  AND "invalidatedAt" IS NULL
  AND "expiresAt" > now()
);

-- 4. OTP Attempt Counter & Consumption Policy (UPDATE Only)
CREATE POLICY stage2_auth_otp_update ON public.auth_otps
FOR UPDATE TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
  AND "consumedAt" IS NULL
)
WITH CHECK (
  public.app_realm() = 'AUTH'
);

-- 5. Customer Portal Contact Login Lookup Policy (SELECT Only)
CREATE POLICY stage2_portal_contact_lookup ON public.customer_contacts
FOR SELECT TO zemifix_app_user
USING (
  public.app_realm() = 'AUTH'
  AND "isActive" = true
  AND "deletedAt" IS NULL
);
```

### 1.4 Protection Against Authentication Abuse Vectors
- **User / OTP Enumeration Prevention:** Login handlers execute constant-time bcrypt comparisons against `DUMMY_HASH` (`auth.ts#L100`) when an email is unknown.
- **OTP Brute-Force & Replay Protection:** `auth_otps` enforces 5-minute expiration windows and locks challenge rows after 3 failed attempts (`attemptCount >= 3`). Consumed OTPs set `consumedAt = now()` and cannot be re-used.
- **IP Rate Limiting:** All authentication endpoints (`/api/auth/login`, `/api/auth/verify-otp`, `/api/portal/auth/login`) enforce strict IP rate-limiting buckets (`rateLimitService.ts`).

## 2. Corrected Authentication Bootstrap Execution Flow (Issue 2)

The previous wrapper draft called `getCurrentUser(req)` BEFORE opening `withSecurityContext`, causing `getCurrentUser()` to query the database using the root `prisma` client outside a signed transaction. Under default-deny RLS, those queries would fail.

### 2.1 Corrected Request Execution Sequence

```
[ Unauthenticated Request: POST /api/auth/login ]
                       │
                       ▼
[ withApiSecurity({ realm: 'AUTH', allowAnonymous: true }) ]
                       │
                       ▼
[ withSecurityContext({ realm: 'AUTH', userId: '' }, callback) ]
                       │
                       ├─► 1. Generates HMAC signature for 'AUTH' realm payload
                       └─► 2. Runs tx.$queryRaw setting set_config('app.current_realm', 'AUTH', true)
                               and signed app.context_signature GUC
                       │
                       ▼
[ getUserByEmail(tx, email) ] ──► (Matches stage2_auth_user_lookup RLS policy)
                       │
                       ▼
[ In-Memory bcrypt Password Verification ] ──► (Validates password hash)
                       │
                       ▼
[ generateOtpChallenge(tx, user.id) ] ──► (Inserts AuthOtp row under signed 'AUTH' context)
                       │
                       ▼
[ Creates Pre-Auth JWT Cookie ] ──► (Issued with audience 'zemifix-preauth')
```

## 3. Backward-Compatible Migration & Deployment Sequence (Issue 3)

Migration `20261119000001_stage2_1_signed_security_context` creates database functions (`app_security_context_valid()`, `app_user_id()`) WITHOUT enabling default-deny RLS. Default-deny RLS is enabled in Migration `20261119000002_stage2_1_default_deny_rls`.

This structure enables a safe 3-phase rollout:

```mermaid

    subgraph Phase A : Database Schema & Key Provisioning
        A1[Apply Migration 20261119000001] --> A2[Run npm run provision:security-context-key]
        A2 --> A3[Verify Key Row & app_security_context_valid Function]
    end

    subgraph Phase B : Application Code Deployment
        B1[Deploy Stage 3 Code Wrappers & Services] --> B2[Run Pre-Migration Integration Tests in Dev]
        B2 --> B3[Drain Web Application & Worker Traffic]
    end

    subgraph Phase C : Default-Deny RLS Enforcement
        C1[Apply Migration 20261119000002 Default Deny RLS] --> C2[Execute Post-Migration Verification Test]
        C2 --> C3[Resume Application Traffic]
    end

    Phase A --> Phase B --> Phase C
```

### Rollback & Failure Recovery Procedures:
- **Phase A Failure:** If key provisioning fails, Migration 1 functions return `FALSE`, but default-deny RLS is NOT enabled on tables, so existing queries continue running normally.
- **Phase B Failure:** If code deployment encounters bugs, rollback code deployment. Database schema remains backward-compatible.
- **Phase C Failure:** If default-deny RLS breaks an unwrapped workflow, rollback Migration 2 (`DROP POLICY stage2_signed_context_required ON ...; ALTER TABLE ... DISABLE ROW LEVEL SECURITY;`).

## 4. Enforceable Prisma Transaction Boundaries (Issue 4)

To prevent developers from importing root `prisma` inside protected services or bypassing security context transactions:

1. **Mandatory Service Signatures:** All service functions in `src/lib/services/` MUST require `tx: Prisma.TransactionClient` as their first parameter.
2. **ESLint Restricted Import Rule:** Configure `.eslintrc.json` rule `no-restricted-imports` prohibiting direct import of `{ prisma }` inside `src/lib/services/` and `src/app/api/`:
   ```json
   "no-restricted-imports": [
     "error",
     {
       "paths": [
         {
           "name": "@/src/lib/prisma",
           "importNames": ["prisma"],
           "message": "Direct use of root prisma client in services/routes is prohibited. Use the transaction client 'tx' provided by withSecurityContext."
         }
       ]
     }
   ]
   ```
3. **Automated AST Coverage Test (`src/tests/apiRouteCoverage.test.ts`):** Uses TypeScript compiler AST parsing to assert that **100% of exported HTTP method handlers under `src/app/api/` are wrapped with `withApiSecurity`**.
4. **Runtime Guard:** Passing an uninitialized transaction client to `withSecurityContext` throws `UNINITIALIZED_TRANSACTION_CONTEXT`.
